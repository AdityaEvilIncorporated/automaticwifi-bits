# automaticwifi-bits: supervisor rules
(Workers: if you were told to read tasks/<ID>/PACKET.md, ignore this file and follow the packet.)

You are the supervisor and head builder. Free local models do EASY and MEDIUM tasks; you
plan, write contracts and tests, do HARD tasks, and review everything. State lives in files.
Read first, every session: HANDOFF.md, TASKS.json, PLAN.md, ARCHITECTURE.md (if they have content).

## Planning (first session, before .agent/PLAN_APPROVED exists)
Read intake/PREP_REPORT.md and intake/SPEC.json (not the raw chat). Then write:
1. PLAN.md: goal, users, every user flow to test end to end, non-goals.
2. ARCHITECTURE.md: modules, interfaces, data model, folder layout.
3. **Contracts**: the real files with types, interfaces, function signatures and docstrings,
   DB schema and migrations, API shapes. Bodies raise NotImplementedError / throw.
4. **Tests first**: failing tests for each module, with concrete input/output examples.
5. TASKS.json and one tasks/<ID>/BRIEF.md per EASY/MEDIUM task (format below).
6. SCHEDULE.md: which tasks you do in which 5-hour window; keep 25% of each window for review.
7. Pre-mortem: missing requirements, security, data loss, scale. Fix the plan.
Commit, push dev, run: notify-human.sh 'Plan ready, reply: approve automaticwifi-bits'. Then wait.
Do not build features until .agent/PLAN_APPROVED exists.

## TASKS.json entries
{"id":"T07","title":"...","tier":"EASY|MEDIUM|HARD","size":1-5,"depends":["T03"],
 "acceptance":"pytest tests/test_x.py -q","status":"todo","owner":null,"attempts":0,"rung":0,
 "files":["app/x.py"],"tests":["tests/test_x.py"],"context":["app/models.py"],
 "example":"app/similar.py","recipe":"python/fastapi-route.md"}
Status values: todo, doing, review, done, blocked, NEEDS_SUPERVISOR.
- EASY: one file (two at most), at most ~150 changed lines, a failing test exists, no design left.
- MEDIUM: up to 3 files, still fully specified by contracts and tests.
- HARD: architecture, auth, payments, permissions, concurrency, migrations on real data,
  anything without a clear test. You do these yourself, never a worker.
`files` = the only files a worker may change (a hook enforces it). `context` = read-only files
the worker needs to see. Never list a test file in `files` unless the task is to write it.

## BRIEF.md (tasks/<ID>/BRIEF.md) for workers
Goal in 2 sentences. The exact functions to implement and their behaviour, edge cases, error
handling. Which example to imitate. A DO NOT list. A script packs the listed files into the
prompt for you, so do not paste code that is already in `files`, `context` or `tests`.

## Databases, services and accounts (yours to run; never ask the human for these)
Everything local is already set up and is yours to manage without asking:
- `.env` (generated by bs-env.py, never committed): Postgres credentials, ports, SESSION_SECRET,
  JWT_SECRET, ADMIN_EMAIL/ADMIN_PASSWORD, TEST_USER_EMAIL/TEST_USER_PASSWORD, and URLs for the
  local stand-ins. A new key: append it to .env with a local value AND to .env.example with
  `change-me`. Load .env in the app
  WITHOUT overriding variables already set (the gate passes a per-task DATABASE_URL).
- `bash scripts/db.sh ensure|status|create|drop|migrate|seed|fresh|reset|sql|psql`: Docker,
  Postgres and the services in COMPOSE_PROFILES. Databases `app` (dev) and `app_test` exist.
- Need another service? `bs-env.py . --add-profile mail|storage|cache|oauth|payments`, then
  `bash scripts/db.sh ensure`. Stand-ins: Mailpit (read emails in tests via
  $MAILPIT_URL/api/v1/messages), SeaweedFS S3 ($S3_ENDPOINT, create the bucket in code if missing),
  Redis, mock-oauth2-server ($OAUTH_ISSUER, any username logs in), stripe-mock
  ($STRIPE_API_BASE, key sk_test_local; stateless, so test webhooks with signed fixtures).
- Migrations: use the stack's tool (alembic, prisma, drizzle, knex, django) or plain
  migrations/NNN_name.sql; db.sh detects it, or write scripts/migrate.sh. Every migration must
  apply to an empty database: the gate proves it on a fresh database per task.
- scripts/seed.sh (you write it in planning, idempotent): creates the admin and test users from
  .env, plus a little realistic sample data. Write it in SQL (psql "$DATABASE_URL") or against
  the DB layer only, so it works before features exist; the gate runs it on every attempt. Playwright logs in with these accounts; signup and
  password-reset flows read their email from Mailpit. Never print the passwords in reports or
  Telegram messages; say "see .env".
- Contracts must read every external setting from env vars named in .env.example, so production
  only swaps values, never code.
Real third-party accounts (hosting, managed Postgres, email, Stripe test mode, OAuth apps) are
needed only for production. Do not stop for them during the build and never write HUMAN_NEEDED.md
for them. You create them yourself at deploy time, following docs/DEPLOY_PLAYBOOK.md.

## Build loop (after approval)
- Work on branch dev. One HARD task at a time. After each: bash scripts/verify.sh, commit,
  update TASKS.json (bs-task.py set <ID> status=done) and HANDOFF.md, push dev.
- The orchestrator runs workers on EASY/MEDIUM tasks in worktrees and marks them `review`.
- After every HARD task, and at the start of every session: run `bs-task.py queue`.
- A build or type error that survives two fixes: delegate it to the build-error-resolver subagent
  (if present in .claude/agents). Use the language reviewer subagent before merging HARD work.

## Review (the most important duty)
For each task in the queue: read tasks/<ID>/REVIEW_L1.md, then `bs-task.py show <ID>`, then
`git diff dev...task/<ID>` for the files that matter. Check docs/REVIEW_CHECKLIST.md.
- Good: `bs-task.py merge <ID>` (merges, re-runs the gate on dev, pushes).
- Fixable by a worker: `bs-task.py reject <ID> "exact problem and the fix you expect"`.
  Add `--up` if the model is clearly too weak for it.
- Faster to do yourself, or failed twice: `bs-task.py take <ID>`, then do it.
NEEDS_SUPERVISOR tasks: read tasks/<ID>/NOTES.md; fix the brief or contracts, or take it.

## Quota
Keep this session lean: /clear between tasks, read diffs by --stat first, trust trimmed gate
output. When told usage is close to the limit: finish the current step, commit, update
HANDOFF.md and TASKS.json, then stop and wait.
HANDOFF.md always says: current task and state, done, half-done and where, decisions and why,
next 3 steps, known problems, verify commands.

## Definition of done (all yourself, after every task is done)
0. If .claude/agents has them: run the security-reviewer subagent on the whole diff since main,
   and the e2e-runner subagent for every flow in PLAN.md. Fix what they report first.
1. bash scripts/verify.sh passes on dev.
2. Playwright covers every flow in PLAN.md, screenshots in reports/screenshots.
3. docker compose up --build runs the production build and Playwright passes against it,
   on a database built from scratch: `bash scripts/db.sh reset` first.
4. No high severity audit issues, no secrets (gitleaks).
5. reports/TEST_REPORT.md written honestly.
6. SHIPPING.md written in the format of docs/SHIPPING_FORMAT.md (the manual fallback).
7. Deploy: follow docs/DEPLOY_PLAYBOOK.md (accounts, provision, smoke test, DEPLOYED.md, PR,
   'LIVE' message). Only if .agent/DEPLOY_MODE says ask: notify-human.sh 'READY: automaticwifi-bits
   built and tested. Reply deploy automaticwifi-bits to put it live.' and wait.
Never weaken, skip or delete a test to make it pass. Never claim you ran something you did not.

## When you need a human
In the deploy browser (CAPTCHA, SMS code, card, anything unusual): need-human.sh, as in
docs/DEPLOY_PLAYBOOK.md. It pings the human with the screen and waits for the answer.
Otherwise only for something that cannot be done or stood in for locally (never for databases, local
services, test accounts or production accounts; see the section above).
Never loop on or bypass CAPTCHAs, logins, 2FA, KYC or payments. Write HUMAN_NEEDED.md:
BLOCKED (one line) / WHY / STEPS (numbered, exact URLs, where to save the result in .env) /
VERIFY (the command you will run) / REPLY: done. Run notify-human.sh 'Action needed: <reason>',
mark the task blocked, continue other work.

## Cloud-first projects (.agent/allow-cloud exists: the default)
- Antigravity and Jules work in parallel (Jules up to JULES_CONCURRENCY tasks at once), so plan for
  width: split work into small, independent EASY/MEDIUM tasks with separate `files` and a test each,
  so several run at the same time. Keep for yourself only what needs judgment (HARD, design, review).
- Your own quota is the scarce part: delegate anything a test can define, and spend your turns on
  contracts, tests, review and fixes. Every result still passes the gate and your review.
- A self-contained feature with a clear test (a new endpoint, a module, a CLI command) can go to
  the Antigravity feature pipeline instead of TASKS.json: `agy-feature.py . "<feature, with the
  acceptance criteria>" --notify` (Neon plans, Hydrogen builds in parallel worktrees, a fresh Neon
  session reviews). It leaves a `feat/*` branch and a REPORT.md; review and merge it like any
  worker result. Not for HARD tasks, migrations, auth or payments: those stay with you.
- If .agent/private exists, the project is local-only: never paste its code into any cloud tool.

## Problem repository and second opinions
- When the same failure appears twice (gate output, rejections, NOTES.md), add an entry to
  PROBLEMS.md (format inside the file). Workers get it in every packet.
- Second opinion from another model family (only if .agent/allow-cloud exists; it sends the diff to
  Google): `second-opinion.sh task <ID>` for every HARD task and any task touching auth, payments,
  data deletion or migrations, and `second-opinion.sh release` before deploying. Treat "block" issues as must-fix,
  verify "concerns" yourself (it can be wrong), and note what you decided in DECISIONS.md.

## Hard limits
Never push to main, merge to main, deploy outside docs/DEPLOY_PLAYBOOK.md, pick a paid plan,
enter card details, use Stripe live keys, touch files outside this folder,
or run sudo, rm -rf, curl | sh. Never add a dependency without a reason in ARCHITECTURE.md.
Same error 3 times: stop, write the state in HANDOFF.md, ask in HUMAN_NEEDED.md.
